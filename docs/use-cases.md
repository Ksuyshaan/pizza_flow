# Сценарии использования (Use Cases) PizzaFlow

Документ описывает прецеденты использования системы для трёх функциональных модулей в соответствии с распределением участников команды.

---

# Модуль 1: Заказы и клиенты (Участник 1)

### UC-1.1: Регистрация нового клиента
- **Актор**: Гость (CUSTOMER).
- **Предусловие**: Пользователь не авторизован.
- **Основной сценарий**:
  1. Гость отправляет запрос регистрации с email, паролем, ФИО и телефоном.
  2. Система проверяет уникальность email и корректность формата данных.
  3. Система хэширует пароль с помощью BCrypt, создаёт запись `User` с ролью `CUSTOMER`.
  4. Система генерирует JWT токен и возвращает его вместе с данными профиля.
- **Альтернативный / Ошибочный сценарий (О1)**:
  - Email уже зарегистрирован в базе данных: система возвращает HTTP 400 Bad Request с сообщением «Пользователь с таким email уже существует».
- **Результат**: Создан аккаунт клиента, клиент авторизован.

### UC-1.2: Добавление адреса доставки
- **Актор**: Клиент (CUSTOMER).
- **Предусловие**: Клиент авторизован.
- **Основной сценарий**:
  1. Клиент указывает город, улицу, дом, квартиру и выбирает зону доставки (`DeliveryZone`).
  2. Система валидирует существование зоны доставки.
  3. Система сохраняет адрес, привязывая его к клиенту.
- **Результат**: Адрес сохранён в профиле клиента.

### UC-1.3: Создание заказа с доставкой и промокодом
- **Актор**: Клиент (CUSTOMER).
- **Предусловие**: Клиент выбрал товары в корзине, авторизован.
- **Основной сценарий**:
  1. Клиент отправляет запрос на создание заказа со списком позиций (ID продукта, количество), типом `DELIVERY`, ID адреса и промокодом.
  2. Система рассчитывает `subtotal` по актуальным ценам продуктов.
  3. Система проверяет промокод (активность, даты, минимальный заказ) и рассчитывает сумму скидки `discountAmount`.
  4. Система определяет стоимость доставки `deliveryFee` согласно зоне адреса и порогу бесплатной доставки.
  5. Система рассчитывает `totalAmount = subtotal - discountAmount + deliveryFee`.
  6. В рамках транзакции создаются `Order`, позиции `OrderItem`, снепшот адреса `deliveryAddressSnapshot` и первая запись в `StatusHistory` (статус `NEW`).
  7. Инкрементируется счетчик использования промокода `timesUsed`.
- **Результат**: Заказ сохранен в статусе `NEW`.

### UC-1.4: Создание заказа на самовывоз (PICKUP)
- **Актор**: Клиент (CUSTOMER).
- **Предусловие**: Клиент выбрал товары в корзине.
- **Основной сценарий**:
  1. Клиент выбирает тип заказа `PICKUP`.
  2. Система рассчитывает стоимость: `deliveryFee` устанавливается равным `0`.
  3. Создаётся заказ в статусе `NEW`.
- **Результат**: Заказ на самовывоз создан с нулевой стоимостью доставки.

### UC-1.5: Ошибка применения промокода (недостаточная сумма заказа)
- **Актор**: Клиент (CUSTOMER).
- **Предусловие**: Клиент оформил заказ на 500 руб. и применил промокод `PIZZA20` (мин. сумма 1200 руб.).
- **Основной сценарий**:
  1. Клиент передает промокод `PIZZA20`.
  2. Сервис проверяет `subtotal >= minOrderAmount`.
  3. Условие не выполняется.
  4. Система выбрасывает `InvalidPromoCodeException` (HTTP 400) с сообщением «Минимальная сумма для промокода PIZZA20 составляет 1200.00 руб.».
- **Результат**: Заказ не создан, клиенту выведено понятное сообщение об ошибке.

### UC-1.6: Отмена заказа клиентом (до начала готовки)
- **Актор**: Клиент (CUSTOMER).
- **Предусловие**: Заказ принадлежит клиенту и находится в статусе `NEW` или `CONFIRMED`.
- **Основной сценарий**:
  1. Клиент запрашивает отмену заказа с указанием причины.
  2. Система проверяет текущий статус заказа (`NEW` или `CONFIRMED`).
  3. Система переводит статус заказа в `CANCELLED`, фиксирует `cancelledAt` и причину.
  4. В `StatusHistory` добавляется запись с автором и комментарием.
- **Результат**: Заказ отменён.

### UC-1.7: Ошибка отмены заказа после начала приготовления
- **Актор**: Клиент (CUSTOMER).
- **Предусловие**: Заказ перешел в статус `COOKING` (ингредиенты уже списаны со склада).
- **Основной сценарий**:
  1. Клиент запрашивает отмену заказа.
  2. `OrderService.changeStatus` проверяет допустимость перехода: переход из `COOKING` в `CANCELLED` запрещён.
  3. Система возвращает HTTP 409 Conflict: «Невозможно отменить заказ после начала приготовления (ингредиенты уже списаны)».
- **Результат**: Статус заказа не изменился, отмена отклонена.

### UC-1.8: Подтверждение заказа менеджером
- **Актор**: Менеджер (MANAGER) или ADMIN.
- **Предусловие**: Заказ в статусе `NEW`.
- **Основной сценарий**:
  1. Менеджер открывает список новых заказов и нажимает «Подтвердить».
  2. `OrderService.changeStatus` переводит заказ в `CONFIRMED`.
  3. Фиксируется `confirmedAt` и запись в `StatusHistory`.
  4. Автоматически инициируется создание наряда на кухню `KitchenService.createKitchenOrder(order.getId())`.
- **Результат**: Заказ подтвержден, на кухне появилась карточка заказа в статусе `PENDING`.

### UC-1.9: Просмотр истории изменения статусов заказа
- **Актор**: Клиент (по своему заказу) или Менеджер (по любому заказу).
- **Предусловие**: Заказ существует.
- **Основной сценарий**:
  1. Пользователь запрашивает историю статусов заказа `/api/v1/orders/{id}/history`.
  2. Система проверяет права (клиент может смотреть только свои заказы).
  3. Возвращается упорядоченный список записей `StatusHistory` (дата, старый статус, новый статус, кто изменил, комментарий).
- **Результат**: Клиент видит хронологическую шкалу обработки заказа.

# Модуль 2: Меню, кухня, склад (Участник 2)

### UC-2.1: Просмотр меню с фильтрацией и пагинацией
- **Актор**: Любой пользователь (гость, клиент, менеджер).
- **Предусловие**: В базе есть активные категории и продукты.
- **Основной сценарий**:
  1. Пользователь запрашивает `/api/v1/products` с параметрами: `categoryId`, `minPrice`, `maxPrice`, `search`, `page`, `size`.
  2. Система фильтрует активные продукты и возвращает список с ценами, описанием и ссылками на фото.
- **Результат**: Отображен отфильтрованный каталог товаров.

### UC-2.2: Взятие заказа в приготовление (startCooking) со списанием сырья
- **Актор**: Повар (COOK) или Менеджер.
- **Предусловие**: Заказ подтвержден (`CONFIRMED`), наряд кухни в статусе `PENDING`.
- **Основной сценарий**:
  1. Повар нажимает «Начать готовить» на кухонном экране.
  2. Сервис `KitchenService` начинает транзакцию.
  3. Для каждой позиции заказа берутся рецептурные нормы `RecipeItem` (продукт * количество позиций).
  4. Для каждого ингредиента проверяется наличие достаточного остатка: `ingredient.getStockQuantity() >= requiredQty`.
  5. С остатка каждого ингредиента вычитается требуемое количество: `stockQuantity = stockQuantity - requiredQty`.
  6. Формируется запись в журнале движений `StockMovement` с типом `CONSUMPTION` и ссылкой на заказ.
  7. Статус наряда кухни переходит в `IN_PROGRESS`, фиксируется `startedAt` и повар.
  8. Статус заказа через `OrderService.changeStatus` меняется на `COOKING`.
  9. Транзакция коммитится.
- **Результат**: Заказ готовится, складские остатки синхронно списаны.

### UC-2.3: Ошибка нехватки ингредиентов на складе (Rollback)
- **Актор**: Повар (COOK).
- **Предусловие**: Заказ содержит пиццу, требующую 200г сыра Моцарелла, а на складе доступно только 50г.
- **Основной сценарий**:
  1. Повар нажимает «Начать готовить».
  2. `KitchenService` выявляет дефицит: `required (200) > stock (50)`.
  3. Выбрасывается исключение `InsufficientStockException` (HTTP 400/409): «Недостаточно ингредиента Моцарелла на складе: требуется 200.0, доступно 50.0».
  4. Транзакция откатывается, ни один ингредиент не списывается, статус заказа остаётся `CONFIRMED`.
- **Результат**: Заказ не переведен в готовку, менеджеру отправлено предупреждение о нехватке сырья.

### UC-2.4: Завершение приготовления (completeCooking)
- **Актор**: Повар (COOK).
- **Предусловие**: Заказ в статусе `COOKING`, наряд кухни `IN_PROGRESS`.
- **Основной сценарий**:
  1. Повар нажимает «Заказ готов».
  2. Статус наряда кухни переводится в `COMPLETED`, фиксируется `completedAt`.
  3. Через `OrderService.changeStatus` статус заказа переводится в `READY`.
  4. Если заказ типа `DELIVERY`, автоматически инициируется создание наряда доставки `DeliveryService.createDelivery(order.getId())`.
  5. Если курьер доступен, запускается автоназначение курьера (FIFO).
- **Результат**: Пицца упакована, заказ готов к выдаче клиенту или передаче курьеру.

### UC-2.5: Оприходование ингредиентов на склад (RECEIPT)
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Прибыла поставка сырья от поставщика.
- **Основной сценарий**:
  1. Менеджер указывает ID ингредиента, поступившее количество (например, +10.0 кг) и комментарий («Накладная №412»).
  2. Система увеличивает остаток `stockQuantity = stockQuantity + qty`.
  3. Создаётся запись `StockMovement` (тип `RECEIPT`, новый баланс, автор, документ).
- **Результат**: Остаток ингредиента на складе пополнен.

### UC-2.6: Списание испорченных продуктов (WASTE)
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Обнаружен бой или истечение срока годности.
- **Основной сценарий**:
  1. Менеджер выбирает ингредиент, указывает списываемое количество и причину списания (`WASTE`).
  2. Система уменьшает остаток и логирует операцию в журнале движений.
- **Результат**: Испорченное сырье списано с баланса ресторана.

### UC-2.7: Конфликт параллельного списания (Optimistic Locking `@Version`)
- **Актор**: Два повара одновременно берут в готовку заказы с одним редким ингредиентом.
- **Предусловие**: На складе остался один стейк лосося.
- **Основной сценарий**:
  1. Оба потока считывают версию ингредиента `version = 3`.
  2. Первый поток успевает списать остаток и коммитит транзакцию, инкрементируя `version = 4`.
  3. Второй поток пытается обновить запись с ожидаемой `version = 3`.
  4. Hibernate выбрасывает `OptimisticLockException` (HTTP 409 Conflict).
  5. Система сообщает об изменении остатков другим пользователем и предлагает обновить данные.
- **Результат**: Целостность склада защищена от гонки данных (race condition).

### UC-2.8: Расчёт нагрузки кухни (Kitchen Load Index)
- **Актор**: Клиент (при оформлении заказа) или Менеджер.
- **Предусловие**: В кухне есть заказы в статусах `PENDING` и `IN_PROGRESS`.
- **Основной сценарий**:
  1. Клиент запрашивает ориентировочное время ожидания `/api/v1/kitchen/load`.
  2. Сервис суммирует время приготовления всех активных позиций в очереди кухни:
     `estimatedMinutes = baseTime + (activeKitchenOrdersCount * avgCookingTime)`.
  3. Возвращается расчётное время в минутах и уровень загрузки (`LOW`, `MEDIUM`, `HIGH`).
- **Результат**: Клиент видит реальный прогноз времени доставки/готовности.

### UC-2.9: Просмотр критических остатков склада (Low Stock Alert)
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Остаток некоторых ингредиентов упал ниже `minStockThreshold`.
- **Основной сценарий**:
  1. Менеджер запрашивает `/api/v1/inventory/low-stock`.
  2. Система выбирает все позиции, где `stockQuantity <= minStockThreshold`.
  3. Менеджер видит список необходимых закупок с дефицитом.
- **Результат**: Предотвращена внезапная остановка работы кухни.

# Модуль 3: Доставка, оплата, отчёты (Участник 3)

### UC-3.1: Автоматическое назначение курьера (FIFO по availableSince)
- **Актор**: Система (фоновый триггер при `Order = READY`) или Менеджер.
- **Предусловие**: Заказ типа `DELIVERY` перешел в статус `READY`, создана запись `Delivery` в статусе `PENDING_ASSIGNMENT`.
- **Основной сценарий**:
  1. Сервис ищет свободных курьеров: `isAvailable == true`.
  2. Список сортируется по времени ожидания: `ORDER BY availableSince ASC` (кто дольше всех ждет заказа — FIFO).
  3. Выбирается первый курьер в очереди.
  4. Курьеру назначается доставка, статус курьера меняется на `isAvailable = false`.
  5. Статус доставки меняется на `ASSIGNED`, фиксируется `assignedAt`.
- **Результат**: Заказ назначен на свободного курьера по справедливой очереди.

### UC-3.2: Обработка ситуации отсутствия свободных курьеров
- **Актор**: Система.
- **Предусловие**: Все курьеры на заказах (`isAvailable == false`).
- **Основной сценарий**:
  1. Сервис пытается назначить курьера, но список свободных пуст.
  2. Запись `Delivery` остаётся в статусе `PENDING_ASSIGNMENT`.
  3. Менеджер видит заказ в блоке «Ожидает курьера».
  4. Как только любой курьер завершит предыдущую доставку, триггер назначит его на старейший ожидающий заказ.
- **Результат**: Заказ не потерян, встал в очередь на распределение.

### UC-3.3: Взятие заказа курьером (Pickup / Выезд)
- **Актор**: Курьер (COURIER).
- **Предусловие**: Доставка назначена на данного курьера (`ASSIGNED`).
- **Основной сценарий**:
  1. Курьер забирает термосумку из ресторана и нажимает «Заказ получен / Везти».
  2. `DeliveryService.pickup` переводит статус доставки в `IN_TRANSIT`, фиксирует `pickedUpAt`.
  3. Статус заказа через `OrderService.changeStatus` меняется на `DELIVERING`.
  4. В `StatusHistory` фиксируется передача курьеру.
- **Результат**: Клиент видит на карте/экране статус «Курьер в пути».

### UC-3.4: Вручение заказа и закрытие оплаты (Complete Delivery)
- **Актор**: Курьер (COURIER).
- **Предусловие**: Доставка в статусе `IN_TRANSIT`.
- **Основной сценарий**:
  1. Курьер передает пиццу клиенту, принимает наличные (при `CASH`) или проверяет онлайн-оплату.
  2. Курьер нажимает «Доставлено».
  3. Статус доставки переводится в `DELIVERED`, фиксируется `deliveredAt`.
  4. Статус связанного `Payment` переводится в `PAID`, фиксируется `paidAt`.
  5. Статус заказа переводится в `COMPLETED`, фиксируется `completedAt`.
  6. Курьер освобождается: `isAvailable = true`, `availableSince = now()`.
- **Результат**: Заказ успешно завершен, выручка зафиксирована, курьер вернулся в конец очереди свободных.

### UC-3.5: Завершение заказа самовывоза менеджером
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Заказ `PICKUP` находится в статусе `READY`.
- **Основной сценарий**:
  1. Клиент приходит в пиццерию, называет номер заказа и забирает коробки.
  2. Менеджер нажимает «Выдать заказ».
  3. `OrderService.changeStatus` переводит заказ сразу в `COMPLETED` (минуя `DELIVERING`).
  4. Оплата переводится в `PAID`.
- **Результат**: Заказ самовывоза закрыт.

### UC-3.6: Возврат платежа при отмене заказа (Refund)
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Заказ с онлайн-оплатой был отменен до начала готовки.
- **Основной сценарий**:
  1. Заказ отменяется в статусе `CONFIRMED`.
  2. `PaymentService.refundPayment(orderId)` инициирует процедуру возврата.
  3. Статус платежа меняется на `REFUNDED`.
  4. В аудит-лог пишется событие возврата средств клиенту.
- **Результат**: Платёж помечен как возвращенный.

### UC-3.7: Формирование аналитического отчёта по продажам в Excel (.xlsx)
- **Актор**: Менеджер (MANAGER) или ADMIN.
- **Предусловие**: В системе есть завершенные заказы за выбранный период.
- **Основной сценарий**:
  1. Менеджер запрашивает `/api/v1/reports/sales/excel?startDate=...&endDate=...`.
  2. `ReportService` с помощью Apache POI XSSFWorkbook строит файл:
     - Лист 1: Сводка продаж (Дата, Количество заказов, Выручка, Средний чек, Доставка, Скидки).
     - Лист 2: Продажи по категориям (Пиццы, Напитки, Десерты, Доля в выручке).
     - Применяется форматирование ячеек: денежные форматы, шапка с заливкой, границы таблиц.
  3. Клиенту отдаётся бинарный поток с заголовком `Content-Disposition: attachment; filename="sales-report.xlsx"`.
- **Результат**: Пользователь скачал оформленный Excel-файл.

### UC-3.8: Формирование отчёта по смене / заказу в Word (.docx)
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Смена подошла к концу.
- **Основной сценарий**:
  1. Менеджер запрашивает генерацию отчёта смены `/api/v1/reports/shift/word`.
  2. `ReportService` через Apache POI XWPFDocument генерирует документ:
     - Титульный блок с логотипом PizzaFlow и датой.
     - Таблица ключевых KPI смены (выручка, заказов доставлено, среднее время доставки).
     - Список курьеров и количество выполненных ими доставок.
     - Раздел инцидентов и отменённых заказов.
  3. Клиент получает скачиваемый файл `shift-report.docx`.

### UC-3.9: Ручное переназначение курьера менеджером
- **Актор**: Менеджер (MANAGER).
- **Предусловие**: Назначенный курьер сообщил о форс-мажоре (поломка транспорта).
- **Основной сценарий**:
  1. Менеджер открывает карточку доставки в статусе `ASSIGNED`.
  2. Выбирает другого курьера из списка доступных.
  3. Предыдущий курьер освобождается (`isAvailable = false` с пометкой поломки).
  4. Новый курьер назначается на доставку.
  5. В журнал аудита заносится запись о ручной замене курьера менеджером.
- **Результат**: Заказ переназначен, задержка минимизирована.
