# Журнал архитектурных решений (Architecture Decision Records)

### ADR-01: Модульный монолит вместо микросервисов
- **Контекст**: Для семестрового проекта из 3 человек критически важно обеспечить прозрачность межмодульного взаимодействия и избежать проблем с распределенными транзакциями и оркестрацией контейнеров.
- **Решение**: Проект строится как модульный монолит на Spring Boot. Модули разделены по пакетам (`order`, `kitchen`, `delivery`, `report`), взаимодействие происходит строго через интерфейсы сервисов.
- **Последствия**: Быстрый запуск, единый контекст БД, надёжные локальные транзакции `@Transactional`, лёгкая проверка на защите.

### ADR-02: Единый статус заказа в `Order`
- **Контекст**: Ранее в проекте статусы дублировались в `Order`, `KitchenOrder` и `Delivery`, что приводило к риску рассинхронизации.
- **Решение**: Главным статусом жизненного цикла признан статус в сущности `Order`. Любое изменение статуса вызывается исключительно через `OrderService.changeStatus(...)`, который валидирует правила переходов и пишет историю в `StatusHistory`.
- **Последствия**: Гарантированная целостность статуса, невозможность "потерять" этап или совершить невалидный переход.

### ADR-03: Упрощенный складской учёт с `@Version` на Ingredient
- **Контекст**: Полноценная система складского партионного учёта с WMS избыточна. Требуется продемонстрировать понимание конкурентного доступа и целостности данных.
- **Решение**: Остаток хранится в поле `stockQuantity` сущности `Ingredient`, защищенной аннотацией `@Version` (Optimistic Locking). Все операции (приход, списание, инвентаризация, брак) фиксируются в журнале `StockMovement`.
- **Последствия**: Простота поддержки, надёжная защита от гонки данных при одновременной готовке блюд несколькими поварами.

### ADR-04: Очередь курьеров FIFO по `availableSince`
- **Контекст**: Реальная геолокация с расчётом расстояний через внешние карты (Яндекс/Google) нестабильна при защите в учебной сети и требует платных API-ключей.
- **Решение**: Курьеры выстраиваются в очередь по справедливому принципу FIFO («кто дольше всех ждёт заказа»). При освобождении курьеру проставляется `availableSince = now()`. Назначение выбирает курьера с минимальным `availableSince`. Зоны доставки задаются тарифными таблицами `DeliveryZone`.
- **Последствия**: Детерминированное, легко тестируемое поведение, 100% соответствие требованиям ТЗ без сторонних зависимостей.

### ADR-05: Единая сущность `User` для всех ролей
- **Контекст**: Разделение на `Customer`, `Employee`, `Manager` порождает избыточные таблицы и усложняет авторизацию через Spring Security.
- **Решение**: Все пользователи хранятся в таблице `users` с перечислением `role` (`CUSTOMER`, `COOK`, `COURIER`, `MANAGER`, `ADMIN`). Дополнительные атрибуты курьера вынесены в таблицу `couriers` со связью 1:1.
- **Последствия**: Чистая модель безопасности, единый эндпоинт входа, прозрачные правила `@PreAuthorize`.

### ADR-06: Формирование отчётов через Apache POI
- **Контекст**: Требуется экспорт отчётов в форматах Microsoft Excel и Microsoft Word.
- **Решение**: Использование библиотеки Apache POI (`poi`, `poi-ooxml`). Сервис генерирует стилизованные `.xlsx` (таблицы продаж, формулы суммирования, доли категорий) и `.docx` (сводка смены, заголовки, таблицы заказов).
- **Последствия**: Формируются настоящие бинарные документы Microsoft Office, открывающиеся в Excel и Word без предупреждений о повреждении файлов.
